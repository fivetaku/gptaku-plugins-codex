## 영수증 지출결의서 — Jev 워크플로 제안

가정: 직원은 지금처럼 카톡으로 사진을 보내고 사진 바로 다음에 용도 한 줄(예: "거래처 3명 계약 협의")을 붙인다. 총무는 금요일에 PC 카톡의 "대화 내보내기"와 사진 일괄 저장으로 폴더 하나를 만든다. 결의서는 지금 쓰는 엑셀 양식을 그대로 채운다. 회의비 1인 한도와 "회의비에 술이 있으면 불인정"이라는 규정 값은 설정 파일에 두고, 회사 규정집의 값을 그대로 옮긴다.

### 한눈에
카톡 사진 약 150장과 용도 메모가 들어온다. 비전 LLM이 영수증 글자만 받아 적는다. Jev가 질문 4종을 고른다. 스크립트가 금액 검산, 주류 처리, 한도 검사를 하고 엑셀 결의서를 채운다. 총무는 확인 표시가 붙은 줄만 보고 팀장 결재로 넘긴다.

```
[카톡 사진+메모] → [비전 LLM: 글자만 JSON] → [코드: 파싱·검산·중복·주류 사전]
                                                   ↓
[엑셀 결의서+확인 목록] ← [코드: 문턱·한도·합계·서식] ← [Jev: 비목·술·목적·참석자]
```

권하는 안은 A입니다. 나머지 두 안은 한 줄씩만 적습니다.
- A(권함): 비전 LLM이 받아 적고 Jev는 글만 읽습니다. 지금 문서 기준으로 운영에 쓸 수 있는 경로입니다.
- B: Jev에 사진을 바로 넣습니다. Jev 1.14는 PNG·JPEG를 받지만 공식 문서가 이미지 기능을 "Dreamer-ready, 운영 준비 전"이라고 적고 있습니다(헤더 `TypeSafe-Danger-Zone-Images: true` 필요, docs.typesafe.ai/images, 2026-11-13 확인). 한국어 영수증 실측도 없어 시험 조건으로만 둡니다.
- C: 비전 LLM이 비목까지 고릅니다. 확률이 나오지 않아 문턱을 정할 수 없고, 같은 영수증에 같은 답이 나온다는 보장도 약합니다.

### 단계별
| 단계 | 누가 | 하는 일 | 넘기는 것 |
|---|---|---|---|
| 입력 | 직원·총무 | 카톡 사진과 메모 제출, 금요일에 내보내기 | 사진 폴더 + 대화 txt |
| 받아 적기 | 비전 LLM(판단 금지 지시) | 상호, 업종 표기, 일시, 품목 줄, 합계, 결제수단, 승인번호를 원문 그대로 적고 안 보이는 칸은 비움 | 영수증별 원문 JSON |
| 전처리 코드 | 스크립트 | 대화 txt에서 사진과 제출자·메모를 짝지음, 금액·일시 파싱, 품목 합계와 총액 검산, 승인번호+금액+일시로 중복 제출 탐지, 주류 사전 적용, 메모에서 "N명" 정규식 추출 | 정리된 state |
| Jev | Jev(한국어 질문) | 비목 Choice, 사전으로 못 가린 품목의 주류 Noul, 회의 목적 기재 Noul, 참석자 기재 Noul | 확률·확실도 |
| 후처리 코드 | 스크립트 | 확실도 문턱 비교, 회의비 주류 처리, 1인당 금액과 한도 검사, 비목·제출자별 합계, 엑셀 채우기 | xlsx 결의서 + 확인 목록 시트 |
| 사람 확인 | 총무 → 팀장 | 총무는 확인 표시 줄만 고치고, 팀장은 지금처럼 결재 | 결재된 결의서 |

전처리 코드의 주류 사전은 두 부분입니다.
- 양성 목록: 소주, 맥주, 생맥, 참이슬, 처음처럼, 카스, 테라, 하이볼, 와인, 막걸리, 사케, 위스키 등.
- 부정 접두어: "무알콜", "논알콜", "0.0" 등이 붙으면 술이 아닌 것으로 확정합니다.

사전이 확정한 품목은 Jev에 보내지 않습니다. 사전에 없는 이름(칵테일명, "하우스 레드", 새 맥주 상표)만 Jev에 물어봅니다.

### Jev 질문 초안
state 예시(영수증 1장 = 요청 1건, 150건 병렬):

```json
{
  "receipt": "한우마을 역삼점 / 2026-11-11 19:10 / 등심 4인 / 공기밥 4 / 켈리 2 / 하우스 레드 1병 / 합계 286,000 / 카드 ****-0000 / 승인 00000000",
  "memo": "고객사 담당자 3명과 계약 협의",
  "submitter": "직원 A",
  "unknown_items": ["켈리 2", "하우스 레드 1병"]
}
```

questions(요청 본문은 `{"model": "jev-1.14.0", "state": …, "questions": …}` 형태):

```json
{
  "category": {
    "type": "choice",
    "instructions": "이 영수증은 지출결의서의 어느 비목으로 처리해야 하는가? `receipt`(영수증에서 읽은 글자)와 `memo`(제출자가 적은 용도)를 함께 보고 판단하라.",
    "criteria": {
      "회의비": "회의·간담회·외부 손님 접대에 쓴 다과·식사. 직원끼리라도 메모에 회의 안건이 적힌 식사는 회의비",
      "식대": "직원 본인들의 끼니(야근 식대 포함). 회의 안건이 없는 직원끼리 식사",
      "여비교통비": "택시·기차·버스·주유·통행료·주차 등 이동 비용",
      "소모품비": "사무용품·전산 소모품·청소용품·비치용 생수·종이컵 등",
      "도서인쇄비": "도서 구입·인쇄·제본·출력·현수막 비용",
      "해당 없음": "개인 지출이거나 업무 용도가 불분명함"
    }
  },
  "alcohol_0": {
    "type": "noul",
    "instructions": "`unknown_items[0]` 품목은 술(소주·맥주·와인·막걸리·하이볼 등 알코올이 든 음료)인가?",
    "criteria": {
      "true": "알코올이 든 음료",
      "false": "음식, 무알콜·논알콜 음료, 술이 아닌 상품"
    }
  },
  "purpose_written": {
    "type": "noul",
    "instructions": "`memo`에 이 지출의 업무 목적(회의 안건, 협의 내용, 행사 이름 등)이 적혀 있는가?"
  },
  "attendees_written": {
    "type": "noul",
    "instructions": "`memo`에 함께한 사람(인원, 이름, 또는 상대 회사)이 적혀 있는가?"
  }
}
```

스크립트가 각 답을 쓰는 곳:
- `category`: 결의서의 비목 칸에 들어갑니다. 확실도가 문턱 아래면 보기 순서를 뒤집어 한 번 더 묻고, 그래도 낮거나 답이 바뀌면 확인 목록으로 보냅니다.
- `alcohol_i`: `unknown_items` 개수만큼 만들고 품목 하나에 질문 하나를 붙입니다. 술 여부는 사전 결과와 합쳐 코드가 정합니다. 개수 세기를 Jev에 맡기지 않기 위해서입니다.
- `purpose_written`·`attendees_written`: 회의비 증빙 칸(목적, 참석자)이 비었는지 확인합니다. 어느 비목이 나올지 몰라도 같은 요청에 미리 싣고, 코드는 비목이 회의비일 때만 이 답을 씁니다. 둘 중 하나라도 "아니오"면 제출자에게 보낼 보완 요청 문장을 템플릿으로 만듭니다.

확인 목록 시트에는 사람이 봐야 할 줄만 모으고, 줄마다 이유를 코드 템플릿 문장으로 적습니다.
- "비목 확실도 낮음(식대 0.58 / 회의비 0.41)" [J][C]
- "품목 합계 271,000 ≠ 총액 286,000, 받아 적기 재확인" [C]
- "회의비 1인당 71,500원, 한도 초과" [C]
- "같은 승인번호가 11-08에도 제출됨" [C]

Jev가 낸 값은 엑셀에서 색으로 구분합니다(Jev 값은 연한 파랑, 원문은 회색, 사람 몫은 노랑). 비어 있는 칸은 지어내지 않고 빈칸으로 둡니다.

### 닮은 사례
1. 작성자 벤치 R3(2026-11-13, jev-1.14.0, 합성 문항)는 이 업무와 같은 질문을 이미 쟀습니다. 영수증 비목 36/36, 주류 포함 14/16이었고, 틀린 쪽은 "무알콜 맥주"를 술로 본 a06이었습니다(확실도 0.62~0.77). 부정어 사전을 코드에 두는 근거입니다. 다만 받아 적기 오류는 이 벤치에 들어 있지 않았습니다.
2. patrol-jev(저자 보고)는 같은 구조로 현장 사진에서 일지를 만듭니다. 사진 30장을 25초에 처리했고, 비전 LLM 받아 적기는 장당 중앙값 4,170ms, Jev 판정은 258ms였습니다. 시간 대부분이 받아 적기에서 나오니, 그 단계를 병렬로 돌리는 것이 속도의 핵심입니다.
3. TypeSafe 공식 쿡북 "OCR confidence and bounding boxes"는 청구서 사진에서 OCR이 읽은 값을 Jev로 다시 확인하는 레시피입니다. 공개 수치는 확인하지 않았습니다. B안 시험을 설계할 때 출발점으로 씁니다.

### 조심할 곳
- **부정어 품목과 새 술 이름.** "무알콜 맥주"는 Jev가 술로 보는 경향이 있고, 확실도도 문턱을 넘을 만큼 높게 나왔습니다(R3). 막는 방법: 부정 접두어 사전이 먼저 확정하고, 사전에 없는 이름만 Jev에 묻습니다. 사람이 고친 품목명은 다음 주 사전에 추가합니다.
- 받아 적기 오류. 금액이나 일자를 잘못 읽으면 Jev가 맞혀도 결의서가 틀립니다. 막는 방법: 품목 합계와 총액을 코드로 검산하고, 승인번호·일시 형식을 검사해 어긋나면 확인 목록으로 보냅니다. 금액은 Jev에 묻지 않습니다.
- 회의비와 식대의 경계. Jev는 적힌 말 그대로 읽기 때문에 "직원끼리 회의 겸 저녁" 같은 경우가 갈립니다. 막는 방법: 경계 사례를 criteria 문장에 넣고, 확실도가 낮은 건은 보기 순서를 뒤집어 다시 묻습니다(첫 보기 편향 대응).
- 실패 방향. Jev 호출이 오류나 시간 초과로 끝나면 그 줄은 자동 처리하지 않고 확인 목록으로 보냅니다. timeout은 성공한 응답의 꼬리보다 길게 둡니다(patrol-jev는 10초로 동작했고 5초에서는 실패).

### 시험 계획
- 표본: 지난 8~12주 실제 영수증 사진 중 100건을 쓰고, 이미 결재된 엑셀 결의서의 비목·주류 판정을 정답으로 삼습니다. 무알콜 품목, 직원끼리 회의 식사, 메모 없는 건 같은 어려운 건을 2~3할 섞습니다. 실행 전에 정답을 해시로 잠급니다.
- 두 층을 따로 잽니다. ① 받아 적기: 금액·일자가 결의서 값과 정확히 일치한 비율. ② Jev: 질문별 정확도, 확실도 구간별 정확도, 보기 순서를 뒤집었을 때 바뀐 건.
- 문턱: 남의 값을 쓰지 않습니다. id 해시로 dev 4할과 holdout 6할을 나눈 뒤, dev에서 "자동 처리 중 오답 0"이 되는 가장 낮은 문턱을 고르고 holdout에서 자동 처리율을 확인합니다. 모델 버전이 바뀌면 다시 고릅니다(R3도 1.13에서 1.14로 바뀌며 0.85가 0.70이 됐습니다).
- 성공 기준: 되돌리기 쉬운 일(총무 확인과 팀장 결재가 뒤에 있음)이므로 holdout 자동 처리 중 오답 0~1건, 자동 처리율 80% 이상이면 시범 운영합니다. B안(사진 직접)은 같은 표본에 조건 하나로만 추가합니다.
- 템플릿: `$PLUGIN_ROOT/skills/golla-jev/bench/`를 작업 폴더로 복사하고 `build_items.py`의 `WF['w1_category']`·`WF['w1_alcohol']` 문항을 실제 표본으로 바꿉니다. 실행 순서는 `build_items.py`, `run.py`, `analyze.py`, `sweep.py`입니다. 키는 비밀 저장소에서 `TYPESAFE_API_KEY`로 주입하고 명령줄에 값을 쓰지 않습니다.
