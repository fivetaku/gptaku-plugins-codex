> 골라제브 0.1.0이 실제로 낸 설계안입니다(설계 모드). 생성 조건: 2026-11-13, 원본 플러그인(golla-jev)만 불러온 헤드리스 에이전트 세션에 아래 요청 한 단락을 넣었습니다. 사람이 고친 것은 내부 경로 표기를 `$PLUGIN_ROOT`로 바꾸고(Codex판은 `$PLUGIN_ROOT`), 대화형 안내 한두 줄을 뺀 것뿐입니다. 업무 내용과 숫자 예시는 가상입니다. Jev API는 호출하지 않았습니다.

**넣은 요청**

> /golla-jev 고객 문의가 많은 5명짜리 B2B SaaS 팀이에요. 공용 받은편지함에 하루 80~120통이 들어오는데, 담당자가 아침마다 읽고 칸반 칸(영업 문의·기술 지원·결제·파트너십·스팸/광고)으로 나누고, 답장이 필요한지 판단하고, 금요일에 주간 처리 현황을 팀장에게 보고합니다. 설계 모드로 끝까지 설계해 주세요.

**점검 결과** (공개 전 점검표)

- 8개 섹션 모두 있음
- 답장 완료·집계·기한 계산은 코드, 결제 피싱은 발신 도메인 화이트리스트로 코드가 먼저 가름
- 수치는 evidence에 있는 것만(칸 32/32, 답장 20/20, GC AI 26/26·0.63→0.92, 피싱 62.6%→95.0%). 보고서 표의 숫자는 예시라고 본문에 밝힘
- 질문 JSON 2블록 파싱됨. 답장 필요를 비대칭 문턱으로 다룸

## 공용 받은편지함 분류·주간 보고 — Jev 워크플로 제안

가정: 메일은 Gmail 또는 Google Workspace 공용 받은편지함에 들어오고, 칸반은 API가 있는 도구(Trello·Notion·Linear 등)를 씁니다. 답장은 계속 사람이 직접 쓰고 보냅니다. 메일은 대부분 한국어이고, 영어 메일이 일부 섞입니다.

### 한눈에
메일(글) → 받아 적기 없음 → 전처리 코드(인용문 자르기, 규칙 분류, CRM 대조) → Jev 질문 5개 → 후처리 코드(문턱 비교, 카드 생성, 집계) → 칸반 카드와 금요일 주간 처리 현황

```
[공용 받은편지함]  →  [전처리 코드]          →  [Jev 한 요청에 5문]     →  [후처리 코드]               →  [산출물]
 10분마다 새 메일     인용·서명 제거,           칸 Choice, 답장 Noul,      확실도를 문턱과 비교,           칸반 카드, '확인 필요' 칸,
                      결제시스템·자동응답은     막힘 Noul, 세일즈 Noul,    스레드는 기존 카드에 붙임,       금요일 보고서
                      규칙으로 분류,            영업 단계 Choice           답장 여부는 발송 기록으로
                      CRM 고객 여부 표시
```

여러 방향이 가능해서 세 안을 비교했고, 이 중 A안을 권합니다.
- **A안 (권함)**: 10분마다 자동으로 카드를 만들고, 확실도가 낮은 메일만 '확인 필요' 칸에 모읍니다. 담당자는 아침에 그 칸만 봅니다.
- B안: 아침에 한 번 몰아서 분류한 뒤 담당자가 전부 승인합니다. 안전하지만 아침 업무가 거의 줄지 않습니다.
- C안: 답장 초안까지 LLM이 씁니다. Jev 역할이 아니고 발송 위험도 따로 따져야 하므로 2단계로 미룹니다.

### 단계별
받아 적기 단계는 없습니다. 입력이 처음부터 글(메일 본문)이기 때문입니다. 첨부 스크린샷은 1단계에서 다루지 않습니다.

| 단계 | 누가 | 하는 일 | 넘기는 것 |
|---|---|---|---|
| 입력 | 코드(Gmail API, 10분 주기) | 새 메일과 스레드 ID를 가져옵니다 | 원본 MIME |
| 전처리 | 코드 | 인용문(`>`, "-----Original")과 서명을 자릅니다. 스레드에 이미 카드가 있으면 그 카드에 댓글로 붙이고 끝냅니다. 결제 시스템 발신(Stripe·토스 등 화이트리스트 도메인)은 규칙으로 '결제'에 넣습니다. `Auto-Submitted`·반송 메일은 규칙으로 '자동 알림'에 넣습니다. 발신 도메인을 CRM과 대조해 `sender.is_customer`를 채웁니다. 메일 주소와 전화번호는 마스킹합니다. 언어를 감지해 질문 세트(한/영)를 고릅니다 | 정리된 state JSON |
| Jev | Jev(`jev-1.14.0`) | 한 요청에 질문 5개를 병렬로 묻습니다. 고르기만 하고 글은 쓰지 않습니다 | 질문별 선택과 확률 |
| 후처리 | 코드 | 확실도를 문턱과 비교합니다. 칸 확실도가 낮거나 1·2위 차이가 작으면 '확인 필요'로 보냅니다. 답장 필요는 비대칭 문턱을 씁니다(아래 '조심할 곳' 2번). 막힘 여부로 긴급 라벨을 붙이고, 영업 단계는 영업 칸일 때만 씁니다 | 카드 필드 |
| 산출 | 코드 | 칸반 카드를 만들고 라벨을 붙입니다. 금요일 17시에 집계 보고서를 만듭니다 | 카드, 보고서 |
| 사람 확인 | 담당자 | 아침에 '확인 필요' 칸만 정리하고, 카드를 옮기면 그 기록이 정답 표본으로 쌓입니다. 팀장 보고서에 한 줄 의견을 적습니다 | 수정 기록, 의견 |

### Jev 질문 초안

state 예시:
```json
{
  "mail": {
    "subject": "RE: API 연동 오류 문의",
    "body": "어제부터 웹훅이 401을 반환해서 주문 동기화가 전부 멈췄습니다. 오늘 오전 중 확인 부탁드립니다. 참고로 다음 달 계약 갱신 때 좌석 20개 추가도 검토 중입니다.",
    "has_attachment": true
  },
  "sender": { "is_customer": true, "plan": "Business" }
}
```

questions:
```json
{
  "column": {
    "type": "choice",
    "instructions": "이 메일은 팀 칸반의 어느 칸으로 가야 하는가? `mail.subject`와 `mail.body`의 새로 쓴 부분을 기준으로 판단하라. 여러 주제가 섞였으면 지금 바로 처리해야 하는 쪽을 고른다. `sender.is_customer`는 기존 고객인지 알려 준다.",
    "criteria": {
      "영업 문의": "우리 제품을 사거나 늘리려는 쪽의 문의: 도입 상담, 견적, 데모 요청, 좌석·요금제 확대",
      "기술 지원": "제품 사용 중 문제나 사용법 질문: 오류, 장애, 연동, 설정, 계정 접근",
      "결제": "청구·결제·환불·세금계산서·영수증·카드 변경 등 돈이 오가는 일",
      "파트너십": "서로 이익이 되는 협업 제안: 리셀러, 연동 제휴, 공동 마케팅, 기술 파트너",
      "스팸/광고": "우리에게 무언가를 팔려는 일방적 영업, 뉴스레터, 광고, 피싱·사칭",
      "해당 없음": "위 어디에도 맞지 않음: 채용 지원, 언론 문의, 개인 연락 등"
    }
  },
  "needs_reply": {
    "type": "noul",
    "instructions": "이 메일을 받은 우리 팀이 답장하거나 무언가를 해야 하는가? `mail.body`의 새로 쓴 부분을 보고 판단하라. 단순 공지, 감사 인사, '회신 안 주셔도 됩니다', 광고는 답장이 필요 없다."
  },
  "blocked": {
    "type": "noul",
    "instructions": "`mail.body`에서 발신자가 지금 우리 서비스를 정상적으로 쓰지 못하고 있다고 말하는가? 장애, 로그인 불가, 데이터 동기화 중단, 결제 실패로 인한 이용 정지 같은 상황이면 예다. 사용법 질문이나 개선 요청은 아니다."
  },
  "cold_pitch": {
    "type": "noul",
    "instructions": "이 메일은 발신자가 우리에게 자기 상품·서비스·리드 DB를 팔려고 보낸 일방적 영업인가? `mail.body`를 보고 판단하라. 우리 제품을 사려는 문의나 양쪽이 함께 일하자는 구체적 제휴 제안은 아니다."
  },
  "sales_stage": {
    "type": "choice",
    "instructions": "이 메일을 영업 문의로 본다면, 발신자는 구매 과정의 어느 단계에 있는가? `mail.body`를 보고 판단하라.",
    "criteria": {
      "정보 탐색": "기능·가격·사례를 알아보는 중",
      "견적·데모 요청": "견적서, 데모, 체험 계정을 구체적으로 요청함",
      "계약 진행": "계약서, 발주, 좌석 확대처럼 구매가 정해진 상태의 실무 이야기",
      "해당 없음": "구매와 관계없는 메일"
    }
  }
}
```

스크립트는 각 답을 이렇게 씁니다.
- `column`: 카드를 놓을 칸을 정합니다. 확실도가 문턱보다 낮거나 1·2위 확률 차이가 작으면 '확인 필요'로 보내고, 두 후보를 카드에 적어 둡니다.
- `needs_reply`: 카드에 '답장 대기' 라벨을 붙이고, 주간 보고서의 미답장 목록을 만드는 기준이 됩니다.
- `blocked`: 칸이 '기술 지원'이나 '결제'이면서 이 답이 예일 때만 '긴급' 라벨을 붙이고 슬랙 알림을 보냅니다. 다른 칸이면 무시합니다.
- `cold_pitch`: 신호 질문입니다. Jev가 칸을 '파트너십'이나 '영업 문의'로 골랐는데 이 답이 예이면 확정하지 않고 '확인 필요'로 보냅니다.
- `sales_stage`: 칸이 '영업 문의'일 때만 카드 라벨로 씁니다. 다른 칸이면 버립니다. 같은 state로 답할 수 있어서 두 번째 요청을 만들지 않고 처음부터 함께 싣습니다.

질문과 보기는 한국어로 쓰고, 보기 이름은 메일에 나올 법한 말 그대로 둡니다. 영어 메일에는 같은 구조의 영어 질문 세트를 씁니다(design-rules §3 "질문·state·보기 이름의 언어를 맞춘다").

### 산출물 모양

칸반 카드 예시:

| 칸 | 내용 |
|---|---|
| 제목 | RE: API 연동 오류 문의 [원] |
| 칸 | 기술 지원 [J] (확실도 0.97) |
| 라벨 | 긴급 [J], 답장 대기 [J], 기존 고객·Business [C] |
| 받은 시각 / 첫 답장 기한 | 11-13 09:12 [C] / 11-13 13:12 (긴급 4시간) [C] |
| 담당자 | [사람] (기술 지원 기본 담당자를 코드가 미리 채움 [C]) |
| 원문 링크 | Gmail 스레드 [C] |

금요일 주간 처리 현황(팀장 보고):

| 칸 | 받은 메일 | 답장 필요 | 답장 완료 | 미답장 | 첫 답장 중앙값 |
|---|---|---|---|---|---|
| 영업 문의 | 64 [C] | 58 [J→C 집계] | 55 [C] | 3 [C] | 2.1시간 [C] |
| 기술 지원 | 181 [C] | 170 [J→C] | 162 [C] | 8 [C] | 3.4시간 [C] |
| 결제 | 47 [C] | 39 [J→C] | 39 [C] | 0 [C] | 5.0시간 [C] |
| 파트너십 | 12 [C] | 9 [J→C] | 6 [C] | 3 [C] | 19.5시간 [C] |
| 스팸/광고 | 203 [C] | — | — | — | — |

보고서의 나머지 부분은 이렇게 채웁니다.
- 긴급 건: 11건 [C], 4시간 안 응답 10/11 [C]
- 영업 단계별 건수: 정보 탐색 31 · 견적·데모 22 · 계약 진행 11 [J→C]
- 사람이 칸을 고친 건수: 17건(이번 주 자동 분류 중 3.4%) [C]. Jev 품질을 보여 주는 지표입니다
- 미답장 목록: 제목 [원], 경과일 [C], 담당자 [사람]
- 이번 주 메모: [사람] 팀장이나 담당자가 적는 칸이고, 자동으로 채우지 않습니다

표의 숫자는 칸 모양을 보이려고 넣은 예시입니다. 답장 완료는 Jev가 판단하지 않고 스레드에 우리 쪽 발송 메일이 있는지로 코드가 셉니다. '고객이 만족했나' 같은 전체적 품질 판단은 넣지 않습니다.

### 닮은 사례
- 작성자 벤치(2026-11-13, `jev-1.14.0`)의 W2 메일 보드는 지금 구조와 거의 같습니다(칸 Choice와 답장 필요 Noul). 칸 32/32, 답장 20/20을 맞혔습니다. 다만 문항이 짧고 깨끗한 합성 메일이라 긴 스레드나 서식 잡음은 반영되지 않았습니다.
- GC AI 해커톤(저자 보고, 2026-10-06)의 받은편지함 분류는 26/26이었습니다. 같은 행사에서 온콜 알림 136건 중 오경보가 1건이었고, 관측값을 state에 넣자 정밀도가 0.63에서 0.92로 올랐습니다. 이 설계에서 `sender.is_customer`와 `plan`을 state에 넣는 근거입니다.
- 피싱 판정(awesome-jev-study #454, 저자 보고)에서 Jev 단독은 62.6%였고, 신호 5개를 회귀로 합치자 95.0%였습니다. 피싱이나 사칭을 Jev 한 질문에 맡기지 않고 `cold_pitch`와 코드 신호(발신 도메인, 링크 도메인 불일치)를 합치는 근거입니다.

### 조심할 곳
1. 결제를 사칭한 피싱("카드 결제 실패, 아래 링크에서 갱신")이 '결제' 칸으로 들어갈 수 있습니다. 실제 결제 시스템 메일은 발신 도메인 화이트리스트로 코드가 분류하고, 그 밖의 결제 메일 중 링크 도메인이 발신 도메인과 다르면 '확인 필요'로 보냅니다. 강한 신호가 그은 선을 확률로 다시 긋지 않는다는 원칙입니다.
2. 답장 필요 판단에서 두 오류의 비용이 다릅니다. 답장이 필요한데 '불필요'로 놓치면 고객을 잃습니다. 그래서 '불필요' 쪽만 높은 문턱(p(아니오)로 따로 정함)을 넘을 때 자동 처리하고, 나머지는 '답장 대기'로 둡니다. 오류나 시간 초과가 나면 '확인 필요'와 '답장 대기'로 둡니다(안전한 쪽으로 실패).
3. '파트너십', 우리에게 파는 콜드 세일즈, 우리 제품을 사려는 영업 문의가 서로 헷갈리기 쉽습니다. criteria에 거래 방향(누가 누구에게 파는가)을 적어 두었고, 신호 질문 `cold_pitch`와 어긋나면 사람에게 넘깁니다.
4. 긴 스레드와 섞인 주제도 문제입니다. 인용문은 코드가 먼저 잘라야 합니다(Jev 약점: 큰 무관 state). 기술 문의와 증설 이야기가 섞인 위 예시처럼 1·2위 확률 차이가 작으면 '확인 필요'로 보내고 두 칸을 카드에 적습니다. 또 Choice는 첫 보기 쪽으로 기우는 편향이 공식 약점에 올라 있으니, 확실도가 낮은 건만 보기 순서를 뒤집어 한 번 더 묻습니다.

이 밖에 고객 메일 본문이 외부 API로 나가므로, 주소와 전화번호를 마스킹하고 TypeSafe의 데이터 처리 조건을 먼저 확인해야 합니다. 키는 서버에서만 읽습니다.

### 시험 계획
- **표본**: 최근 2~3주 메일 150건. 지금 칸반의 칸 이동 기록이 이미 정답 후보입니다. 칸마다 최소 20건을 넣고, 어려운 건(제휴와 콜드 세일즈, 피싱, 섞인 주제, 영어, 긴 스레드)을 2~3할 섞습니다.
- **정답 붙이기**: 담당자 기록을 정답으로 쓰되, 30건은 다른 팀원이 따로 붙여 사람끼리 일치율을 잽니다. 사람끼리 갈린 건은 따로 표시합니다. 실행 전에 해시로 잠급니다(`lock.txt`).
- **문턱 정하기**: id 해시로 dev 4할, holdout 6할로 나눕니다. ko, ko_rev(보기 순서 뒤집기), packed(묶음) 조건을 2회씩 돌립니다. 문턱은 dev에서 '자동 처리 중 오답 0'이 되는 가장 낮은 확실도로 고릅니다. 칸, 답장 필요(아니오 쪽), 막힘을 따로 정하고, 남의 문턱은 쓰지 않습니다.
- **성공 기준**: holdout에서 자동 처리 중 오답 0~1건, 자동 처리율 80% 이상이면 2주 동안 그림자 운영을 합니다. 이 기간에는 사람 분류를 계속하고 결과만 비교합니다. 운영에 들어간 뒤에는 사람이 고친 카드를 표본에 계속 더하고 모델이 바뀔 때마다 문턱을 다시 맞춥니다.
- **템플릿**: `$PLUGIN_ROOT/skills/golla-jev/bench/`를 작업 폴더로 복사한 뒤, `build_items.py`의 `WF['w2_cat']` 보기를 위 6칸으로 바꾸고 `w2_reply`에 실제 메일을 넣습니다. 실행 순서는 `build_items.py`, `run.py`(키는 비밀 저장소에서 `TYPESAFE_API_KEY`로 주입), `analyze.py`, `sweep.py`입니다.

모델과 가격은 docs.typesafe.ai에서 2026-11-13에 다시 확인했습니다. 현재 모델은 `jev-1.14.0`, 입력 $0.042/1M 토큰이고 출력은 무료입니다. 1.14부터 이미지 입력도 받으므로, 오류 스크린샷 첨부를 state에 넣는 일은 2단계 후보로 둡니다.

### 첫 걸음
반나절 분량입니다. 공용 받은편지함에서 최근 2주 메일 100건과 칸반 칸 기록을 내보내 인용문을 자르고, bench의 `w2_cat`·`w2_reply`만 바꿔 ko와 ko_rev 조건으로 한 번 돌립니다. 결과 표에서 칸별 정확도와 확실도 구간별 정확도를 보고, '확인 필요'로 빠지는 비율이 몇 %인지 확인합니다.
