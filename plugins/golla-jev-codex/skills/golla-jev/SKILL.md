# 골라제브 (golla-jev) — "골라 골라"는 Jev에게 맡긴다

핵심 한 줄: **업무 속 "고르는 순간"을 찾아 Jev에게 넘기고, 나머지는 각자 잘하는 담당에게 나눈다.**
목표는 판정이 아니라 **구현 가능한 워크플로 제안**이다. Jev가 맞지 않는 부분이 있어도 버리지 않는다.
그 부분은 코드·LLM·사람에게 배정한 채로 전체 흐름을 완성해 보여 준다.

## 기본 그림 (모든 제안의 뼈대)

```
[입력]        [받아 적기 · 눈]          [Jev · 스위치]              [스크립트 · 손]            [산출물]
사진·녹음·   → 멀티모달/STT가 본 것과  → 닫힌 질문에 확률로 답   → 문턱 비교·계산·묶기   → hwpx·xlsx·보드·
메일·로그       글자만 적는다(판단 X)      (고르기만, 쓰지 않음)       템플릿 문장·실행           알림·행동
```

- 입력이 처음부터 글·JSON이면 받아 적기 단계는 없다.
- 스크립트는 Jev 앞에서도 일한다: 시각·금액·날짜 파싱, 목록 대조, 계산. Jev에는 정리된 재료만 넘긴다.
- 최종 결정권자는 스크립트다. Jev는 확률을 내고, 스크립트가 문턱과 비교해 실행·보류·사람 넘김을 정한다.

## 두 가지 모드

- **아이디어 모드** — "우리 회사(업무)에 제브 쓸 데 있어?"처럼 대상이 넓을 때. 업무를 훑어 고르는 순간 후보를 3~5개 뽑고, 후보마다 한 줄씩 적는다: 무엇을 고르나 · 질문 타입(Choice/Noul/Score) · 하루 몇 건 · 틀리면 되돌리기 쉬운가. 되돌리기 쉽고 건수 많은 것을 1순위로 권하고, 사용자가 고르면 설계 모드로 넘어간다.
- **설계 모드** — 업무 하나가 정해졌을 때. 아래 절차와 출력 형식대로 끝까지 설계한다.

어느 모드인지 애매하면 아이디어 모드로 시작한다. 묻지 않는다.

## 절차

1. **설명을 업무 단위로 쪼갠다.** 무엇이 들어오나(형태·양·빈도), 지금 사람이 무엇을 보고 무엇을 고르나, 결과로 무엇이 나가나(문서·행동). 모르는 칸은 통상적 디폴트로 채우고 "가정:"으로 적는다. 질문은 결과가 갈라질 때만 1회.
2. **판단 지점을 뽑는다.** 사람이 고르는 순간마다 Choice/Noul/Score 중 하나로 바꾼다. 계산·날짜·개수·정확한 대조는 판단이 아니라 코드다. 글 생성·전체적 품질 평가는 Jev가 아니라 템플릿 또는 LLM이다. `references/design-rules.md`
3. **가장 가까운 패턴을 찾는다.** `references/patterns.md`의 job 12종·사무 문서 5종·특이 사례에서 고르고, 닮은 공개 사례와 수치를 붙인다. 수치는 `references/evidence.md`에서만 가져온다(출처·저자 보고 여부 표기).
4. **산출물을 설계한다.** 사무직 대상이면 "그 조직의 서식"으로 나오게 한다(있어빌리티). 문장은 코드 템플릿, Jev는 칸을 채울 값만. hwpx가 필요하면 `references/doc-output.md`.
5. **시험 계획을 붙인다.** 표본 수, 정답 붙이는 법, dev/holdout 문턱 절차, 무엇을 재는지. `references/test-plan.md`
6. **버전 의존 사실은 실측한다.** 현재 모델 ID·가격·한도·SDK 호출법은 `typesafe:typesafe-ai` 스킬 또는 `https://docs.typesafe.ai/llms.txt`에서 읽는다. 기억으로 적지 않는다.

## 출력 형식

```markdown
## {업무 이름} — Jev 워크플로 제안

가정: …(있을 때만 한 줄)

### 한눈에
{입력} → {받아 적기} → Jev 질문 N개 → {스크립트} → {산출물}
(ASCII 흐름도 3~6칸)

### 단계별
| 단계 | 누가 | 하는 일 | 넘기는 것 |
(입력 / 받아 적기 / 전처리 코드 / Jev / 후처리 코드 / 산출 / 사람 확인 — 해당 없는 단계는 행을 빼고 "받아 적기 없음: 입력이 글" 처럼 한 줄로 적는다)

### Jev 질문 초안
state 예시 JSON 1개 + questions JSON(타입·instructions·criteria). 질문 3~6개.
각 질문 옆에 "이 답을 스크립트가 어디에 쓰는지" 한 줄.

### 산출물 모양
실제 문서 일부를 미리보기로(표·양식 칸). 칸마다 출처 기호를 붙인다: [J] Jev 값 · [C] 코드 계산 · [원] 받아 적은 원문 · [사람] 사람 몫.

### 닮은 사례
2~3개. 무엇이 같고 수치가 얼마인지, 출처. 저자 보고면 그렇게 적는다.

### 조심할 곳
이 워크플로에서 실제로 틀리기 쉬운 지점 2~4개와 막는 방법(design-rules 근거).

### 시험 계획
표본 N건 · 정답 방식 · 문턱 절차 · 성공 기준. 바로 돌릴 수 있게 이 스킬의 `bench/` 템플릿 경로(`$PLUGIN_ROOT/skills/golla-jev/bench/`)를 준다.

### 첫 걸음
가장 작게 돌려 볼 한 단계(반나절 분량).
```

- 여러 방향이 가능하면 2~3안을 짧게 보이고 하나를 권한다. 권하지 않은 안은 한 줄씩만.
- 수치·사례에는 출처를 단다. 작성자 실측은 "작성자 벤치(날짜, 당시 모델)", 외부는 "저자 보고".
- 응답은 사용자 언어를 따른다(기본 한국어).
- 플러그인 안 파일은 `$PLUGIN_ROOT/skills/golla-jev/...` 표기 그대로 적는다. 사용자 컴퓨터의 절대경로로 풀어 쓰지 않는다(설계안을 남에게 넘길 때 경로가 새지 않게).
- 이미지 입력은 문서상 가능하지만 운영 준비 전이다. 사진이 들어오는 업무는 받아 적기 단계를 기본안으로 두고, 사진 직접 입력은 시험 조건으로만 제안한다(`references/evidence.md`). JSON의 instructions·criteria 언어 선택은 design-rules §언어를 따른다.

## 하지 말 것

- "Jev가 맞다/안 맞다"로 끝내기. 안 맞는 부분은 다른 담당에게 배정하고 흐름을 완성한다.
- 남의 문턱값(0.6·0.7 등)을 그대로 권하기. 문턱은 시험 계획으로 정한다.
- Jev에게 글을 쓰게 하거나, 계산·날짜 세기를 맡기기.
- 근거 파일에 없는 수치를 만들어 붙이기.
- 확인 안 한 API 필드·버전을 단정하기.
